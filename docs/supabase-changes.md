# Supabase Changes and Setup Notes

This file explains the database and Auth work behind the registration flows, and the migrations that add live scoring and paper entry. It is written for teammates who are joining the project after the changes were made.

## What Supabase stores

- `auth.users` stores the login email and account metadata such as name, age, location, phone, experience, and horse details.
- `profiles` stores the permanent user id and the authorization role: `player`, `judge`, `commentator` or `admin`. A signup trigger creates the profile row as a `player`; administrators assign the other roles from the Profiles tab.
- `solo_registrations` stores one solo event entry and links to `profiles.id` through `profile_id`. It also holds the rider's optional `father_name` and `mother_name`, and `registration_source` (`online` or `paper`) with `entered_by` (the administrator who keyed in a paper form). A paper entry has no account, so its `profile_id` is null until the rider claims it.
- `teams` stores the team name, its leader profile id (null for a team entered on paper), `registration_source` and `entered_by`.
- `team_members` stores the four rider rows for a team, each with its own optional `father_name` and `mother_name`. Non-leader rider rows are linked to the person by their normalized email address. This is the intended design, not a placeholder — see "Email is the rider's identity" below.
- `registration_drafts` stores one in-progress solo form or team-wizard draft per user so registration progress survives logout and device switches. Drafts are plain form text (jsonb), readable and writable only by their owner, and deleted when the registration is submitted.
- `scoring_rounds`, `scoring_runs`, `scoring_live_state` and `scoring_advance_overrides`, with the `scoring_leaderboard` view, hold live scoring: the rounds of the day, one row per pass of one rider at one peg, the single "what is live now" row, and administrators' decisions on who goes through. They are readable by anyone (the public scoreboard needs them) and writable only through service-role database functions. A run carries a copy of the rider's name, horse, team and home location, so nothing public ever reads a registration table.

## Live migrations already applied

These migration names are present in the current Supabase migration history:

1. `lock_profiles_prevent_role_self_escalation` prevents browser users from changing their `profiles.role`. Role changes go through the server-only admin API.
2. `enforce_max_four_team_members` adds a database trigger that rejects a fifth rider on a team.
3. `registration_data_integrity_constraints` adds required-column, age, experience, horse-age, email-format, and other data checks to both registration paths.
4. `revoke_execute_on_trigger_only_functions` removes direct execution of enforcement trigger functions from client roles.
5. `revoke_execute_from_public_on_trigger_functions` corrects the previous revoke by removing the default `PUBLIC` execute grant as well.
6. `text_field_length_caps` limits names, locations, breeds, phone numbers, emails, and team names to safe lengths.
7. `lock_profiles_insert_path` removes client INSERT access and the old insert policy from `profiles`. The signup trigger still creates the profile because it runs as a security-definer trigger.
8. `registration_drafts_autosave` adds the `registration_drafts` table (one autosaved draft per user per registration type, owner-only RLS, size-capped jsonb payload, `updated_at` refresh trigger). This is the first migration whose SQL is also committed in the repo, under `supabase/migrations/`.
9. `harden_admin_audit_log` makes audit actors server-trusted, stores actor name/email snapshots, preserves audit rows when an administrator is deleted, removes browser write access to the audit table, and adds service-role-only transactional functions for registration edits and role changes.
10. `lock_admin_registration_write_paths` removes the old broad admin UPDATE/DELETE RLS policies from registration tables. Admin dashboard writes must now use the protected server route, while players and team leaders keep their existing owner-scoped permissions.
11. `registration_confirmation_codes` adds `confirmation_code`, `checked_in_at` and `checked_in_by` to `solo_registrations` and `team_members`, generates a code on every insert through a trigger, backfills the rows that registered before codes existed, and replaces the table-wide `authenticated` UPDATE grant with an explicit column list that excludes all three new columns.
12. `admin_rider_check_in` adds the service-role-only `admin_set_check_in()` and `admin_find_rider_by_code()` functions used by the check-in desk.
13. `one_confirmation_code_per_rider` makes the code belong to the rider rather than the registration. A rider may enter solo *and* ride on a team; the insert trigger now reuses their existing code (matched on normalized email) instead of issuing a second one, and `admin_set_check_in` is re-keyed from a single row id to the code, updating every entry that code covers in one transaction. Without this, checking in the solo entry left the same rider showing as absent on their team roster — skewing the "all four must check in" rule and potentially holding a present section out of the brackets. Also collapses any rider already holding two codes, though none existed when it was written.
14. `rider_headshots` adds a **private** `rider-headshots` storage bucket with owner-scoped policies: objects live at `<profile_id>/<file>` and every policy pins the first path segment to `auth.uid()`, so a browser cannot write outside its own folder. Administrators get read-only access for check-in identity confirmation. The path is stored in Auth user metadata as `headshot_path`, so the photo follows the person rather than one registration.
15. `team_member_horse_name` adds `horse_name` to `team_members`. It is nullable with a length-only check: eight rider rows predate the field, and a NOT NULL constraint would block any future update to those rows. New registrations are required to supply one by the submit route.
16. `admin_edit_team_horse_name` lets administrators edit a team rider's horse name, which `admin_mutate_registration` omitted because it predates the column. The function is patched in place from `pg_get_functiondef` rather than retyped — it is ~7 KB guarding every admin write and its audit record — and both substitutions are asserted so an unrecognised body fails loudly. Note the asymmetry it preserves: `team_members.horse_name` is nullable so the admin route treats it as optional, while `solo_registrations` has a NOT VALID `horse_name_required` check that Postgres enforces on every UPDATE — so the seven solo rows still missing a horse name cannot be edited until one is supplied.

Migrations 11 and 12 were applied to the live project on 28 July 2026 and verified there: all 13 solo registrations and 8 team riders received a valid, distinct code, with no collisions across the two tables; both insert triggers and all four functions are present; `authenticated` retains UPDATE on exactly the intended data columns (11 on `solo_registrations`, 8 on `team_members`) and on none of `confirmation_code`, `checked_in_at` or `checked_in_by`.

## Live scoring and paper entry migrations (committed October 2026, not yet applied)

These five are committed under `supabase/migrations/` and are applied by hand in the Supabase SQL editor, in this order. Section 5 of [live-stream.md](live-stream.md) has the steps and the verification queries. Each file is idempotent and checks its own preconditions (17, 20 and 21 also check their results), so running one twice changes nothing and a database of the wrong shape fails loudly instead of being half-changed. Each ends with `notify pgrst, 'reload schema'` so the API sees its changes at once. **Apply 17 before the code that uses it goes live**: the solo form, the team submit route and `/account` read and write the parents' names.

17. `20261025100000_rider_parent_names` adds `father_name` and `mother_name` to `solo_registrations` and `team_members`, so the commentary panel can introduce a rider the way the announcer does ("son of …"). Both are **optional on purpose**: registrations keep arriving right up to check-in, and the names help the announcer rather than decide who rides, so a required field would turn entries away over a detail the event does not depend on. They are nullable with a length check (1–200 characters when present); rows registered earlier stay null and remain editable. If the organisers later want them required, enforce it in the submit routes, not with NOT NULL, which would make every older row uneditable. Because migration 11 replaced the table-wide UPDATE grant with a column list, new columns are not covered by it, so SELECT, INSERT and UPDATE are granted on both columns explicitly — otherwise a rider's own edit would silently drop them. `admin_mutate_registration` is patched in place (the same asserted `pg_get_functiondef` technique as migration 16) to accept and write both names; a blank box becomes null, and an edit whose payload lacks the keys (a dashboard tab loaded before the release) keeps the stored names. `admin_find_rider_by_code` is dropped and recreated (its return type changes) to return both names to the check-in desk, and its team branch now returns the rider's own `horse_name`, which it had returned as null because the function predates migration 15.
18. `20261025110000_staff_roles` adds two staff roles: `judge` (records results at `/judge` and reads `/commentary`) and `commentator` (reads `/commentary`). The original CHECK on `profiles.role` was created in the dashboard, so its name is not known for certain: every CHECK on `profiles` whose definition mentions `role` is looked up in `pg_constraint`, dropped (and reported as a NOTICE), and replaced by one named `profiles_role_check` allowing the four roles; an existing value outside them stops the migration and is named. `admin_set_profile_role` is replaced with the same signature and grants, so `/api/admin/users` calls it unchanged and it stays the only role write path (the self-escalation lock from migration 1 still applies). It keeps the audit action names `promote_admin` and `demote_admin` and uses `set_role` for changes between the other roles, with the old and new role in the details either way. `has_role(variadic text[])` is the role-list counterpart of `is_admin()`: security definer and recursion-safe for the same reason, it only ever answers about the caller's own row (`auth.uid()`), and it is granted to `authenticated` only. A read-only storage policy, "Staff read every headshot", mirrors the administrators' one for judges and commentators. Nothing about `is_admin()` changes, so a judge gains no access to the registration tables, the audit log or `/admin`. The commentary panel currently signs headshot URLs on the server with the service role and does not depend on this policy; its effect on the live bucket has not been verified.
19. `20261025120000_live_scoring` is the whole database side of live scoring: `scoring_rounds`, `scoring_runs`, `scoring_live_state` (a single row: the live round, the rider on course, the pool called to the start, what the screens show and the announcement message), `scoring_advance_overrides`, and the `scoring_leaderboard` view. It refuses to run before migration 18. The design choices:
    - **Read-only from the browser.** All four tables have RLS with a permissive SELECT policy for `anon` and `authenticated` and nothing else. Everything is revoked first (Supabase's default privileges would otherwise hand the browser roles full access) and SELECT granted back. The overrides table is granted by column, so the public can see that an override exists and which way it went, but not the administrator's note or who set it.
    - **Function-only writes.** Every change goes through one of 14 `scoring_*` functions: record, clear and skip results, move the live pointer and change what the screens show, call a pool, create and edit rounds, draw and clear start lists, add, remove and move entrants, and overrides. (Nine more are internal helpers and two are trigger functions; none of the 25 is callable by a browser role.) They are security invoker with an empty `search_path` and executable by `service_role` only, so the only way in is a server route that has already checked the caller's role. Each locks what it changes, validates the transition, and writes its `admin_audit_log` row in the same transaction. Errors meant for a person use `P0002` (not found) or `22023` (not allowed now) with a sentence fit to show a judge on a phone; the routes pass only those through. A fixed locking order (the live state, then the round, then its runs in run order) keeps two judges and an administrator from deadlocking. Two judges cannot both score one run: the second is refused unless they explicitly choose "Change result".
    - **A public snapshot on every run.** A run stores the rider's name, horse, team and home location when the start list is drawn, so the scoreboard, overlays and data feeds never read a registration table. Ages, phone numbers, emails, parents and emergency contacts are never copied. A `before insert` trigger checks each run against the real registration row and derives `entrant_key` (`solo:<id>` or `team:<id>`). `points` is generated from `result` (carry 4, strike 2, miss 0), so the browser never sends points. A unique key with `nulls not distinct` (Postgres 15+) stops a rider being given two runs for the same attempt.
    - **A carry ends a rider's qualification.** In a Single round with more than one attempt, one carried peg qualifies the rider, so `scoring_record_result` voids their remaining pending attempts in the same transaction and records the carrying run in the new `auto_voided_by` column; the live pointer moves past them. Clearing that carry, or changing it to another result, puts them back through the internal helper `scoring_restore_auto_voided` (or hands them to the rider's other carry, if there is one). Restoring a run by hand clears the marker. A check keeps `auto_voided_by` only on void runs, and the audit row lists which runs were voided or restored.
    - **Registrations in a start list cannot be deleted.** The identity checks make the `on delete set null` on a run's registration ids impossible to complete, so deleting a registration that appears in any start list fails. That is intended: recorded results cannot vanish with a registration. Remove the entrant from the round first.
    - **The leaderboard view** (`security_invoker`, so it can never show more than the tables do) ranks entrants per round and per pool. Single: the best run counts; a rider is through as soon as they carry, and out once all attempts are ridden without one. Section: the four riders' runs added up; through when the total reaches the round's target, decided once all four have ridden. An override row wins over the rule. Skipped runs are left out of the counts.
    - **Pools** are drawn exactly as `balancedPoolSizes` in `src/lib/scoring/types.ts` computes them: the fewest pools of roughly `pool_size`, sizes differing by at most one, labelled A, B, C … in draw order.
    - **Realtime.** `scoring_rounds`, `scoring_runs` and `scoring_live_state` are added to the `supabase_realtime` publication (skipped where the publication does not exist or already covers every table). Realtime honours RLS, so the anonymous SELECT policies are what let the public scoreboard subscribe. Whether the live project's Realtime delivers these events to anonymous browsers has not been verified yet; every page falls back to polling when it does not.
    - **The undocumented `score_attempts` and `solo_scoresheet` tables are left untouched by design.** Live scoring was built alongside them under new `scoring_*` names, so nothing collides and nothing reads or writes the old tables (see "Live schema not represented in this repo" below).
20. `20261025130000_paper_registrations` lets an administrator key in a rider who registered on the printed form, through `admin_create_paper_registration`. It is service-role only; the route at `/api/admin/paper-registration` verifies the administrator first, and the function checks again that the actor is an admin. One transaction validates the form with the same bounds as the online paths, refuses a rider who is already registered, inserts the entry, lets the existing trigger assign the confirmation code(s), and writes one audit row per registration (`paper_registration`). An advisory lock takes paper entries one at a time, so two administrators keying in the same stack cannot both pass the duplicate checks. It refuses to run before migration 17. The deliberate choices:
    - **A paper rider has no account.** `solo_registrations.profile_id` and `teams.leader_profile_id` become nullable (only if they are still NOT NULL; the migration also refuses to continue if a CHECK still demands an account). Owner-scoped RLS compares those columns with `auth.uid()`, which never equals null, so paper rows are visible to administrators only until claimed.
    - **Placeholder emails on an unclaimable domain.** When the form has no email, the rider is stored under `no-email-<12 random characters>@paper.nezabazipunjab.com`. That keeps the NOT NULL, UNIQUE and format checks and the one-code-per-rider trigger working unchanged. The domain receives no mail and **must never be given MX records**: a rider is linked to an account by a confirmed email address, and an address nobody can confirm can never be claimed. `src/lib/email/resend.ts` refuses to send to it, and the app displays it as "No email (paper entry)".
    - **The one-code-per-rider rule (migration 13) still decides codes.** It runs on insert and matches on email, so a placeholder never matches anyone and a rider without email always gets a fresh code, while a paper rider whose email is already on an entry of the other kind shares that entry's code. The duplicate rules follow from it: the same email or phone on the same kind of entry is refused; the same email across solo and team is allowed (one rider in both events, one code); the same phone across kinds under a different or missing email is refused, because it would give one rider two codes (or is a typing mistake). Phones are compared by their digits. Because codes are assigned on insert, replacing a placeholder later does not change the rider's code.
    - **Where a row came from.** `registration_source` (`online` or `paper`, default `online`) and `entered_by` on `solo_registrations` and `teams`, readable by signed-in users like the rest of the row. A table-wide INSERT grant cannot have one column revoked from it, so a `lock_registration_source` trigger pins the browser roles instead: a row they insert is always `online` with no `entered_by`, and their updates cannot change either column.
    - **One known limitation.** A paper rider without an email cannot also be entered in the other event: their phone is already on the first entry, and a placeholder address cannot be shared to link the two entries, so the phone rule refuses the second. The remedy is a real email address on both (the administrator replaces the placeholder on the first entry, then keys in the second form with the same address), after which both share one code.
    - **Claiming a paper solo entry.** Team riders need nothing extra: they are matched by email like every team rider. A solo row is otherwise found by `profile_id`, so once an administrator has replaced a placeholder with the rider's real address and the rider signs up and confirms that address, the account sync (`src/lib/supabase/sync-registration-profile.ts`, service role) claims the row by setting `profile_id` — paper rows only, unclaimed rows only, and only when the user has no solo entry yet. From then on it is synced from the account like any online entry.
21. `20261026100000_scoring_short_location` makes a run's location snapshot district and state only. Migration 19's insert trigger copied the registered location whole ("Village, District, State, Country"), and the village is the rider's own address, while `scoring_runs` and `scoring_leaderboard` are readable with the public key (by design, for the scoreboard and realtime) and realtime pushes the raw row to every open browser. The public API already cut the location on the way out (`toPublicRun` in `src/lib/scoring/types.ts`); this stops the full address being stored at all. It refuses to run before migration 19 and can be applied any time after it. The deliberate choices:
    - **One rule in two languages.** `scoring_short_location(text)` is the SQL twin of `shortLocation` in `src/lib/scoring/types.ts` and must agree with it: split on commas, trim each part (the characters JavaScript's `trim()` removes, not just spaces), drop empty parts; two parts or fewer are joined unchanged, otherwise the two before the last ("Rehearsal Village, Amritsar, Punjab, India" → "Amritsar, Punjab"); blank or null → null. It is immutable, strict, security invoker with an empty `search_path`, and executable by `service_role` only, which is enough: its one caller, the insert trigger, is security invoker and so runs as whoever inserts the run (`service_role` through the `scoring_*` functions, or the project owner in the SQL editor). The migration's own check runs five fixtures against it, and `public-state.test.mts` runs the same five against `shortLocation`. It is the 26th `scoring_*` function.
    - **The trigger is patched, not retyped.** `scoring_runs_before_insert` is patched in place with the asserted `pg_get_functiondef` technique of migrations 16 and 17: its location assignment is wrapped in `scoring_short_location(…)`, the anchor must occur exactly once, a second run is a no-op, and a body that has drifted from migration 19 stops the migration. Whatever the start-list builder passes and whatever the trigger fills from the registration, the stored value is the short form. Re-running migration 19 puts the original trigger back, so run 21 again after it.
    - **Runs already drawn are shortened.** One UPDATE rewrites only the rows whose location is not already short (there were none on the live project when this was written), taking the live-state row first like every scoring function so it cannot interleave with a judge's write. The `updated_at` trigger stamps those rows and realtime sends one event each. Neither matters: nothing ranks or decides by a run's `updated_at` (it only keys a viewer's refetch), and no score, status or order changes, so there is no audit row.
    - **Staff lose nothing.** The commentary panel reads the village from the registration, not from the run.

22. `20261026120000_audit_log_archive` adds `admin_audit_log_archive` and the service-role-only `admin_archive_audit_entries()`. Deleting from the dashboard's Audit Log page (one entry, a selection, or Clear all) moves the rows to the archive in one transaction, stamped with who removed them and when, instead of destroying them. The archive is readable by administrators only, has no browser write access, and has no restore path. Until it is applied, deleting from the tab fails and removes nothing.
23. `20261028120000_scoring_rehearsal_feed` adds `scoring_rehearsal` (a single row: whether the moving vMix rehearsal sample, `?sample=solo`, is running, when it last changed and who changed it) and the service-role-only `scoring_set_rehearsal_sample()`, which flips it and writes its audit row (`start_rehearsal_feed` / `stop_rehearsal_feed`) in the same transaction. It is off by default. The public can read the switch and when it changed through a column grant, never who changed it, because the vMix feeds read it with the public key. It touches no existing table, can be applied any time after migration 19, and was applied to the live project on 28 Oct 2026. Until it is applied, the **Graphics Rehearsal Feed** card on `/admin/scoring` says "Not set up yet" and `?sample=solo` answers like `?sample=1`.

## Confirmation codes and check-in

Every rider receives a unique `NBP-XXXXXX` code when they register — solo entrants and all four riders on a team, one code each.

- **Generated in the database.** Solo registrations are inserted straight from the browser under RLS, so a code chosen by app code could be forged. A `before insert` trigger overwrites whatever arrived and clears the check-in columns, making a self-checked-in registration impossible at insert time.
- **Random, not sequential.** A sequential number would leak the total registration count to anyone holding a code and let a stranger guess a valid one. It would also collide with the separate bracket numbering that gets assigned once registration closes — those are two different identifiers.
- **Unique across both tables.** The desk types one code and the lookup searches solo entrants and team riders together, so a shared code would be ambiguous.
- **Readable aloud.** The alphabet omits `O/0`, `I/1` and `U`.
- **Not writable from a browser.** Postgres cannot revoke a single column from a table-wide UPDATE grant, so the grant was replaced with an explicit column list. `confirmation_code`, `checked_in_at` and `checked_in_by` are simply absent from it, leaving the audited admin route as the only write path.

Check-in runs the day before the event. An administrator enters the code, sees the rider's record and — for a team rider — how many of the four have arrived, then confirms. Checking in an already-checked-in rider raises rather than silently overwriting the original arrival time and the administrator who recorded it. Undo is available and audited the same way.

## Registration emails

The confirmation-code email goes through the **Resend API directly**, using a server-only `RESEND_API_KEY`. This is separate from the Resend SMTP settings in the Supabase dashboard: those only cover Auth emails (confirm signup, recovery, email change) rendered from Supabase's own templates, and cannot send application email.

Sending is best-effort on purpose. It happens in `after()`, so it never blocks a registration that already committed, and a missing key is a logged skip rather than an error. The code is always shown on-screen and on `/account`, and the team success page lists all four riders' codes so the leader can pass them on — riders 2-4 have no account here, so email is otherwise their only channel.

## Live schema not represented in this repo

The live project also contains two tables with no migration in `supabase/migrations/`, no entry in this document's history above, and no application code referencing them:

- `score_attempts` — `round_number`, `result` (`miss`/`touch`/`hit`), a generated `points` column (`hit` = 4, `touch` = 2, else 0), `recorded_by`, and foreign keys to both `solo_registrations` and `team_members`. This matches the agreed scoring rules. Currently empty.
- `solo_scoresheet` — `rounds` (jsonb), `total_override`, `sort_order`, `updated_by`. Currently holds 7 rows.

These appear to have been created directly in the Supabase dashboard. They are harmless where they stand, but they are undocumented drift: nothing in the repo would recreate them in a fresh project, and nothing reads or writes them. Live scoring (migration 19) was built alongside them under new `scoring_*` names and leaves both untouched by design. Once it is in use, they can be dropped after checking that the seven `solo_scoresheet` rows are not needed.

The live database was checked after these changes: existing rows satisfy the constraints, teams have four riders, and teams have one leader. The Supabase security advisor still has intentional or deferred warnings for public trigger-function execution, leaked-password protection, and some RLS performance policies.

## Application data flow

1. A user signs up or logs in through Supabase Auth.
2. The signup trigger creates a basic `profiles` row with role `player`.
3. Account details are read from Auth metadata, not copied into `profiles`.
4. Solo registration writes through the authenticated Supabase client and is protected by RLS plus database checks.
5. Team registration submits to `/register-team/submit`, where the server validates all four riders, checks duplicate emails and phones, creates the team, and inserts the roster.
6. Account saves go through `/api/account/profile`. The route authenticates the session, updates Auth, and uses the server-only service role to synchronize matching registration rows.
7. The account page shows a rider's membership on another person's team by matching the current login email. That match is the identity link, by design.
8. Admin registration changes go through `/api/admin/registrations`. The route verifies the administrator, derives the audit actor from that session, and calls a service-role-only PostgreSQL function that commits the data change and audit record together. Admin Auth changes remain in `/api/admin/users`; email changes and deletions create a required audit record before calling Supabase Auth, and role changes use an atomic database function.
9. Staff roles (judge, commentator, admin) are assigned from the Staff page (`/admin/staff`) through `/api/admin/users`, which calls `admin_set_profile_role`. The staff pages and every scoring route read the caller's role from their own `profiles` row on the server (`src/lib/scoring/auth.ts`), never from anything the browser sends.
10. Paper entries go from `/admin/paper` to `/api/admin/paper-registration`, which verifies the administrator and calls `admin_create_paper_registration` with the service role. The confirmation-code email is sent after the response, and never to a placeholder address.
11. Results and the live pointer are written from `/judge` (judges and administrators) and `/admin/scoring` (administrators) through the routes under `/api/judge/` and `/api/admin/scoring/`. Each route checks the role, derives the audit actor from the session, and calls one service-role `scoring_*` function that commits the change and its audit record together.
12. The public scoreboard, the stream overlays and the four vMix data feeds (current, leaderboard, entrants, rounds) read `/api/live/state` and `/api/live/vmix/*`, which are assembled through the **anonymous** role from the `scoring_*` tables and the leaderboard view only, and cached at the edge for a second. `/live` also reads earlier rounds' standings from the view directly with the browser's anonymous client. Realtime change events on the scoring tables tell every open page to refetch, with `?v=<commit timestamp>` on the URL so the edge cannot answer with its copy from before the write; without Realtime, pages poll. `?sample=1` on a vMix feed answers with fixed rehearsal data and never reads the database.
13. The commentary panel reads `/api/commentary/state` (judges, commentators, administrators), which adds each rider's background — parents' names, age, home, experience, horse, team and a short-lived signed headshot URL — from the registration tables through the service role. It is the only scoring path that touches registration data for staff screens, and its responses are never cached.
14. The rider list for the graphics team, `GET /api/admin/scoring/export` (administrators only), reads the registration tables through the service role and writes a CSV (or JSON) of riders with team, horse, district and state, experience, check-in and current pool. It selects no phone, email, age, parents' names, emergency contacts or full address, and no confirmation code — the code is the rider's check-in credential and must never leave the organisers.

## Environment and deployment

Local development needs all three variables in `.env.local`:

```text
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_ANON_KEY=
SUPABASE_SERVICE_ROLE_KEY=
GEONAMES_USERNAME=
RESEND_API_KEY=
RESEND_FROM_EMAIL=
```

`RESEND_FROM_EMAIL` is optional and normally left unset. The verified sending domain in Resend is `mail.nezabazipunjab.com`, not the apex `nezabazipunjab.com`, so the default sender is `NezaBazi Punjab <no-reply@mail.nezabazipunjab.com>` — the same address the Supabase Auth templates send from. Setting this to an apex address makes Resend reject every application email with a 403 and no email goes out, while registration still succeeds.

Never put real values in `.env.example` — it is the one `.env*` file `.gitignore` does not ignore, so anything pasted there is published on the next commit.

`GEONAMES_USERNAME` is optional and server-only: it enables the village autocomplete in the location picker (register free at geonames.org and enable "free web services" on the account page). Without it, the picker falls back to manual village/city entry.

## Email confirmation, password reset, and auth links

The production domain is `https://www.nezabazipunjab.com`, and the app side is built for confirmation and recovery emails sent through Resend. Dashboard state cannot be verified from the repository, so do not consider confirmation live until every checklist item below has been confirmed in Supabase and Resend:

- `/auth/confirm` (route handler) verifies the emailed one-time token and establishes a session, then redirects to an internal `next` path. It accepts both link styles — `token_hash` + `type` (via `verifyOtp`, works across devices) and `code` (via `exchangeCodeForSession`, default templates, same browser) — and sends failures to `/auth/auth-code-error`.
- Signup calls `signUp` with `emailRedirectTo` and, when confirmation is on, shows a "check your inbox" success page instead of logging in. After the confirmation callback establishes the session, it syncs the verified account metadata into any solo or team-member row already using that email.
- `/forgot-password` sends a reset link (`resetPasswordForEmail`); `/reset-password` sets the new password (`updateUser`) from the recovery session. A "Forgot password?" link sits on `/login`.
- Account email changes no longer stamp an unconfirmed address onto registration rows (`syncEmail: false` while a change is pending). After the user confirms, the next sign-in's POST sync reconciles the solo row by `profile_id`.
- Signup and password reset require at least 8 characters in the app; use the same or a stronger minimum in Supabase.

Dashboard settings to apply/confirm in Supabase (Authentication → URL Configuration and Email Templates):

1. **Custom SMTP**: confirm Supabase Authentication email settings use the verified Resend sender domain and that a real test email is delivered.
2. **Confirm Email**: enable it under Authentication → Providers → Email.
3. **Site URL**: `https://www.nezabazipunjab.com`
4. **Redirect URLs** (allowlist): `https://www.nezabazipunjab.com/**` and `http://localhost:3000/**` for local dev. Add only the specific Vercel preview pattern you use if preview auth testing is needed.
5. **Email templates** — for reliable cross-device links, point each action link at the confirm route with the token hash. Examples:
   - Confirm signup: `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&amp;type=signup`
     — no `next` here. On the signup path the route signs the user out and sends
     them to `/login?redirect=…` using the destination captured at signup time
     (defaulting to `/register`), so a `next` parameter is ignored. Escape the
     ampersands as `&amp;` in the template HTML: a bare `&` in an attribute is
     invalid and some clients drop everything after it, which would break `type`.
   - Reset password: `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&amp;type=recovery&amp;next=/reset-password`
   - Change email address: `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&amp;type=email_change&amp;next=/account`
   - Magic link (if used): `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&amp;type=magiclink&amp;next=/account`

   These three take the normal path, so `next` is honoured — it is sanitized to an
   internal path by `getSafeRedirect`, so an external URL cannot be smuggled in.

   If a template is left on the default `{{ .ConfirmationURL }}`, the `code` fallback in `/auth/confirm` still works as long as the link is opened in the same browser that started the request.
6. **Password policy**: set the minimum to at least 8 characters and enable leaked-password protection under Authentication → Policies if the project plan supports it.
7. **Resend tracking and limits**: disable click/open tracking for authentication email, then set Supabase's email rate limit to a deliberate value within the Resend plan rather than leaving it unreviewed.
8. **End-to-end verification**: with a brand-new email, test signup → confirmation → account/team details, unconfirmed login, an expired link, forgot password → reset → login, and an email change. Open at least one confirmation and one recovery link on a different device or private browser session.

## Google sign-in

Offered on both `/login` and `/signup` beside the password form. The code is in place; it stays inert until the provider is configured in the two dashboards below.

- `/auth/callback` (route handler) is where Google returns the rider. It exchanges the PKCE `code` for a session and sends failures — including a refused consent screen, which arrives as `?error=` rather than a missing code — to `/auth/auth-code-error`. It is deliberately **not** `/auth/confirm`: that route signs the user out mid-flow on a first email confirmation, which would end the session an OAuth sign-in just opened.
- **Account collision is handled by Supabase, not by us.** Supabase links an identity to the existing user whenever the email matches, so signing in with Google at an address that already has a password account resolves to that same user id — the solo row keeps its `profile_id` and the team row keeps its email match. When it links, Supabase also drops any unconfirmed identity on that user, which is what prevents a pre-account-takeover: someone who signs up with an address they do not own cannot keep a foothold once the real owner arrives through Google.
- **Google supplies no age, location, or phone** — only email, name, and avatar. All three are required to register, and `syncRegistrationProfileFromUser` refuses to run without them. So a new Google account is redirected to `/complete-profile` before anything else, which collects them through the same `PATCH /api/account/profile` the account page uses. Returning Google users and all password accounts pass straight through.
- `/register/solo` and `/register-team` re-check the same condition and bounce an incomplete account back to `/complete-profile`. Both render the rider fields locked and filled from the account, so without that guard a bookmark or back button would land someone on blank boxes they cannot type into.
- The email is read-only on `/complete-profile`. It arrives verified from Google and is what every entry is matched on; changing it belongs on the account page, where the confirmation flow that protects it runs.

Dashboard settings to apply (nothing works until both are done):

1. **Google Cloud Console** → APIs & Services → Credentials → Create OAuth client ID → Web application. Set the authorized redirect URI to `https://<project-ref>.supabase.co/auth/v1/callback` (Supabase's callback, not this site's). Configure the OAuth consent screen; while it is in "Testing" only listed test users can sign in, so publish it before riders are pointed at it.
2. **Supabase** → Authentication → Providers → Google: enable it and paste that client ID and secret.
3. **Redirect URLs**: the existing allowlist entries cover this — the button builds its callback from the live origin, so `https://www.nezabazipunjab.com/**` covers production and `http://localhost:3000/**` covers local dev. Add a preview pattern only if Google sign-in is tested from a preview deployment.
4. **End-to-end verification**, in this order: a brand-new Google address (expect `/complete-profile`, then the destination), the same address a second time (expect straight through), and — the collision case — a Google sign-in at an address that already has a confirmed password account, checking afterwards on `/account` that the existing registration is still attached rather than a second account having appeared.

One case this does not solve: Gmail treats `first.last@gmail.com` and `firstlast@gmail.com` as one inbox, but they are different strings and Supabase treats them as two users. A team leader who types the dotted form while the rider's Google account is undotted will produce an entry that does not link. Normalizing it is not safe to do blindly — the dot rule is Gmail's alone and does not hold for Workspace domains — so it is left alone and noted here.

## Email is the rider's identity

A rider is connected to their entries by their normalized email address. This is a deliberate design decision, not an interim measure — do not plan work to replace it with verified `profile_id` linking.

It follows from how team registration works: riders 2–4 are entered by their leader and may have no account here at all, so the address the leader typed is the only thing that can identify them. A rider claims their entry by signing in with that address, and their confirmation email tells them to do exactly that.

What makes it sound is that a **confirmed** email is the boundary. Every registration path checks `hasConfirmedEmail` before it will write anything, so possession of an unverified address grants nothing.

Two consequences to design around rather than fix:

- A rider's email change does not reach their rows on a team someone else leads — those rows are matched on the address they already hold. The admin dashboard's email-sync dialog is the intended remedy for this, not a workaround.
- Whoever controls an address can claim the entries under it. That is the same trust model as password reset, and it is why the confirmation step is not optional.
