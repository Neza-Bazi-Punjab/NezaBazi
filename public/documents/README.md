# Rules Document

Drop the official rules PDF here as `rules.pdf`:

```
public/documents/rules.pdf
```

The [/rules](../../src/app/rules/page.tsx) page checks for this file at build
time — once it exists, the page automatically switches from the "coming
soon" placeholder to an embedded viewer with a download link. Rebuild
(`npm run build`) or restart the dev server after adding the file.

## Dimension diagrams

Three separate reference sheets sit alongside the rulebook, listed in the
Dimensions section of the same page with View and Download buttons:

```
public/documents/ground-dimensions.pdf
public/documents/barshi-dimensions.pdf
public/documents/peg-dimensions.pdf
```

Each is listed only when its file is present, so a missing one drops out
rather than producing a dead link. Filenames are lowercase and hyphenated on
purpose: spaces become `%20` in URLs and get mangled by some clients.

To add another diagram, drop the PDF here and add an entry to the `diagrams`
array in [the rules page](../../src/app/rules/page.tsx).

Each diagram is paired with a compressed image under
`public/images/diagrams/<slug>.jpg`, which is what the Rulebook page shows in
the card grid and the full-size modal. The PDF is the download. A diagram
appears only when **both** files exist, so a half-added diagram drops out
rather than rendering a broken card.

## Registration forms

The printable paper registration forms, linked from [/register/paper](../../src/app/register/paper/page.tsx):

```
public/documents/registration-form-solo.pdf   one rider, 1 page
public/documents/registration-form-team.pdf   four riders, team leader first, 2 pages
```

Do not edit these by hand. They are generated by
[scripts/build-paper-forms.mts](../../scripts/build-paper-forms.mts) with
`npm run build:forms` (Node 24), from the event details in
[src/lib/site.ts](../../src/lib/site.ts) and the field list in
[src/lib/paper-registration.ts](../../src/lib/paper-registration.ts), which the
admin entry panel at /admin/paper also reads. Rebuild them when either changes,
then commit both PDFs. The Punjabi labels need Noto Sans Gurmukhi, which the
script downloads into `scripts/fonts/` on first run (not committed); if the
download fails it still builds the forms, English only, and says so.

Two rebuilds are not byte-identical (the embedded font subset gets a random
name), so a rebuild always shows as a change: rebuild only when the form
should change, and never regenerate them in CI. Like the diagrams, each form is
listed on the page only when its file is present.

## Staff guide

The event-day guide for organisers, judges, commentators, the check-in desk
and the graphics team, "How the live scoring works", linked as **Staff guide
(PDF)** in the admin dashboard's tab bar:

```
public/documents/staff-guide.pdf   A4, about 12 pages, one section per job
```

Do not edit it by hand. It is generated by
[scripts/build-staff-guide.mts](../../scripts/build-staff-guide.mts) with
`npm run build:guide` (Node 24). The wording lives in
[docs/superpowers/plans/2026-10-25-staff-guide-outline.md](../../docs/superpowers/plans/2026-10-25-staff-guide-outline.md)
(the notes at its top explain the few formatting rules), the event facts come
from [src/lib/site.ts](../../src/lib/site.ts), and the screenshots it shows
are in `scripts/staff-guide/`. Edit the outline, rebuild, then commit the
outline and the PDF together. It uses only the PDF's built-in fonts, so the
build needs no network, and a rebuild with nothing changed gives the same
bytes. When a panel's buttons or labels change, update the outline (and
retake the affected screenshot) so the guide keeps matching the screens.

## vMix guide

The graphics team's handout, "Live scoring data for vMix": the four live data
feeds, every column, rehearsal with `?sample=1` and an event-day checklist,
linked as **vMix guide (PDF)** in the admin dashboard's tab bar and as
**Handout (PDF)** on the [/overlay](../../src/app/overlay/page.tsx) setup page:

```
public/documents/vmix-guide.pdf    A4, about 9 pages, one section per task
```

Do not edit it by hand. The same script and command build it, alongside the
staff guide: `npm run build:guide` runs
[scripts/build-staff-guide.mts](../../scripts/build-staff-guide.mts), which
builds every guide in its `GUIDES` table. Its wording is the handout itself,
[docs/vmix-data-feed.md](../../docs/vmix-data-feed.md), so the Markdown and the
PDF cannot drift apart: edit the Markdown, rebuild, then commit both together.
The notes at the top of that file explain the few formatting rules; the site
title and contact email come from [src/lib/site.ts](../../src/lib/site.ts),
and its two screenshots are the staff guide's, in `scripts/staff-guide/`. When
a feed gains, loses or renames a column (`src/lib/scoring/vmix-columns.ts`),
update the handout's column tables and rebuild.

## Rehearsal guide

"Rehearse the live scoring": how staff practise alone on the training pages,
and the run sheet for the team's one dress rehearsal before event day (test
riders entered as paper entries, a throwaway round, a twelve-step run sheet
with what every screen should show, the cleanup and a pass checklist). The
staff guide's Practising section points to it:

```
public/documents/rehearsal-guide.pdf   A4, 6 pages
```

Do not edit it by hand. The same `npm run build:guide` builds it, from
[docs/superpowers/plans/2026-10-26-rehearsal-guide-outline.md](../../docs/superpowers/plans/2026-10-26-rehearsal-guide-outline.md)
(same formatting rules as the staff guide). It has no screenshots of its own:
it reuses one from `scripts/staff-guide/`. Edit the outline, rebuild, then
commit both together. When a button or label on the scoring, judges',
commentary or paper-entry pages changes, check the run sheet's wording too.
